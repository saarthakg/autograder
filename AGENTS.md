# Development process

This project was built with Claude Code as the implementer, with the author as reviewer and decision-maker. The agent wrote most of the code. A separate Claude agent served as a second reviewer for the plan and for each phase report; the author made the calls and set the direction. This document records the rules the agent was held to, and the points where holding them changed the result.

## Working rules

- **Phase gates with review.** Work ran in phases: plan, foundation, grading and eval, product, load test, final pass. At the end of each phase the agent stopped and reported what was done, what it decided, what it was unsure about, test results and its commits. Nothing moved forward or was pushed until the author had reviewed it. Decisions the agent could not make alone went into `DECISIONS.md` for the author to approve or change.
- **Spend approval.** Before any eval or real-model run, the agent printed a projected cost, and anything over $2 required approval. A budget guard in the app refuses model calls below a credit floor. The whole project used about $0.27 of model credit.
- **Git rules.** Small logical commits that each build and pass tests, with conventional messages. Only the author's name on commits: no co-author or tool trailers, and no changes to git config. Before every push, two scans: one for attribution lines and one for API keys across the full history. Secrets and private notes stay gitignored.
- **APIs verified against source.** Effect v4 is new and changes quickly, so the agent checked every API against a pinned clone of the Effect repository rather than relying on memory. That check found the repository it had been pointed to was archived, prompting the switch to the canonical one (D-16).
- **SLOs before load tests.** The pass/fail bar was fixed before the first run: zero lost work checked against the database, latency and time-to-grade targets at a stated load, and a validity gate so a slow load generator cannot produce a false pass (D-22). Verdicts come from those numbers.

## Where direction changed the outcome

- **The hard set caught the fallback.** The 20-case eval rated three cheap models as equally good. A small set of adversarial cases, added on the author's request, showed the intended fallback model confidently "reading" an unreadable scribble and awarding 3 of 4 points on every run. A teacher would never catch that error, so the fallback was replaced (D-30).
- **The transfer budget caught a real bug.** The database's free tier allows 5 GB of transfer a month, shared with production. The author capped the load test at 2 GB and required each run to project its transfer before starting. The measurement showed every student poll carrying the submitted drawings, a regression from an earlier UI change that every test had missed. It was fixed before the large runs (D-31).
- **Re-measure, don't claim.** The load test found the first breakpoint, and the agent proposed raising concurrency as the fix. The author required the change to be applied and re-measured at 2× and 4×, with the reasoning shown via Little's law and the untested assumption stated plainly: the provider has to accept that concurrency. The claim became a measured result (D-32).
- **Simplifying the hosting.** This change came from the author's own push-back. The first hosting plan had grown to a second deployed environment, a separately deployed fake model, and the cloud setup around them. It was cut to one service and one database, with the simulator inside the app and the load test aimed at the real public URL. That kept the infrastructure proportional to the requirements and kept the focus on the product (D-28).
